Admin and install guide

How to install, secure, back up, and recover the OEP delivery stack. There are two install paths: the online one-command path and the signed air-gap path for machines with no network at all. Both finish on the same health checks.

1. Prerequisites (every install)

  • Ubuntu 24.04 (aarch64 or amd64) or Debian 12, on a U1/VM-class host. The NAS is the repository and storage host only; it never runs Keelworks services.
  • Docker Engine 24+ running (docker info) and Docker Compose v2.
  • About 5 GB free disk, curl, git.
  • Online path: outbound internet to fetch build base images and crates. Air-gap path: the signed offline bundle instead (below).

2. Online install (one command)

git clone http://gitea/keelworks/keelworks.git keelworks
cd keelworks/P10-M1/deploy
./install.sh

The script preflights Docker/Compose/disk, writes .env from .env.example (host binds default to 127.0.0.1 so nothing is exposed to the LAN), builds the single stack image, starts the services, waits for every health check, and curls each surface. Exit 0 iff all surfaces answer green.

ServiceBinaryHost address (default)Health surface
pdmoep-pdm127.0.0.1:8787GET /api/v1/health
vieweroep-web127.0.0.1:8790GET / (200)
p2poep-opsdash127.0.0.1:8080GET /healthz
docsoep-docs127.0.0.1:8792GET /healthz

Manage the stack with ./install.sh --down (stop), --no-build (reuse the image) and, for bundling, ./release.sh 0.1.0 --tarball --out ../releases which produces the offline image tarball plus a .sha256 checksum.

3. Air-gap install (no network at all)

An air-gapped shop has a machine with no default route, no DNS, and no registry. The signed offline bundle is the single artifact that crosses the gap (USB stick or ISO). Everything the target needs is inside it. There is no reach-back, no phone-home, no registry pull, and no runtime that talks to a vendor cloud.

The flow: build on a connected host → transfer by USB/ISO → verify on the target → load → configure → start → verify → rollback on failure. None of the target steps touch the network.

On the connected build host

cd scripts/airgap
gpg --import keys/oep-airgap-signing.pub.asc
export SIGN_KEY_ID=oep-airgap-signing
./build-offline-bundle.sh --version 0.1.0 \
    --images keelworks/oep-pdm:0.1.0 \
    --compose docker-compose.airgap.yml \
    --out dist/

Output: keelworks-offline-0.1.0.tar.gz (the bundle), .sha256 (media checksum), and .sig (detached signature, P11).

On the air-gapped target

sha256sum -c keelworks-offline-0.1.0.tar.gz.sha256
sudo ./airgap-verify.sh --bundle /media/usb/keelworks-offline-0.1.0.tar.gz
sudo ./airgap-install.sh \
    --bundle /media/usb/keelworks-offline-0.1.0.tar.gz \
    --install-dir /opt/keelworks --project oep

airgap-install.sh verifies the bundle gpg signature and its sha256, extracts and verifies the signed MANIFEST (every file's checksum is checked, so a tampered bit anywhere fails install), docker-loads the embedded images (no pull), writes a fresh /opt/keelworks/.env with a new local secret and OEP_UPDATE_CHECK=off by default, brings the stack up, waits for the same health checks as an online install, and records proof/airgap-install-record.json as the audit record. If health never comes up it rolls back; it never leaves a half-broken stack pretending to be healthy.

4. TLS

oep-pdm terminates TLS natively (no reverse proxy required). For a zero-config LAN identity, generate a local CA + leaf and point the PDM at it: 

scripts/gen-stack-certs.sh P10-M1/certs    # ca.pem, cert.pem, key.pem (+chain)
oep-pdm --persist-dir <vault> --tls-cert P10-M1/certs/cert.pem --tls-key P10-M1/certs/key.pem
  • --tls-cert and --tls-key must be given together; otherwise the server refuses to start (exit 2). Plain HTTP is not served on the TLS listener.
  • Rotate the certs before 27 months (the script's RSA validity). For production, mount real PKI certs and point --tls-cert / --tls-key at them.
  • Verification of the whole stack is openssl s_client -verify_return_error -CAfile, and the health JSON rides over TLS.

5. Backup (daily, checksummed, to a second disk)

The vault (metadata DB + content-addressed blobs + tamper-evident audit chain) is snapshotted to a second disk or archive target:

scripts/backup/vault-backup.sh <BK_TARGET>   # write bundle + self-verify
scripts/backup/install-vault-backup-cron.sh    # schedule it daily
scripts/backup/vault-restore-check.sh          # restore round-trip proof
  • The producer writes a sha256 manifest over every bundle file and self-verifies (sha256sum -c) before exiting 0.
  • Blobs are content-addressed and each name is checked against the sha256 of its bytes.
  • The NAS is passive storage and is never a backup target by policy.

6. Disaster recovery

The quarterly DR runbook restores the full vault from the P10-M1 backup to a fresh U1/VM-class machine in under 60 minutes, verified by health checks and a real vault read. Run scripts/dr/drill-restore.sh or the manual procedure in P10-M3/dr-runbook.md. Schedule an off-cycle drill whenever the vault schema, backup layout, restore procedure, or a release train changes.

7. Update posture (decision 11)

The update checker is advisory, non-blocking, disable-able, and off by default. The program runs identically whether the checker finds a server, finds nothing, or cannot reach anything; no update gate ever prevents launch. It polls a configurable source (remote URL, on-site mirror, or an offline signed bundle placed by an admin), verifies signed manifests before any payload, and never fails closed. Telemetry stays out (P0-M5-T02).

8. Health checks, honest summary

Every install path ends on the same contract: PDM /api/v1/health, viewer GET / 200, p2p /healthz, and docs /healthz. Success is measured, not assumed; air-gap installs record an audit file on the target. If a step cannot be shown green, the install is reported as failed and (air-gap) rolled back.
