Security

Security

This page tells you two things: how to report a security issue, and how to prove that a release you downloaded was really made by the Isolith release lane. The full policy lives in SECURITY.md in the repository.

Report privately first

A vulnerability in Isolith is not a public issue. Do not open a public issue, pull request, or discussion that describes an exploitable weakness or includes a working exploit. Report it privately to security@isolith.dev. A report should name the release or commit you tested, the component and version, the steps to reproduce, and the impact you observed (a severity guess is a claim; label it as one). A report reaches the maintainer explicitly, so the safe harbor in the policy applies from the moment it is sent privately.

What you can expect

  • Acknowledgement within 3 business days.
  • An initial assessment (valid, invalid, needs more information) within 7 business days of acknowledgement.
  • A disposition: fixed, being fixed with an estimate, or declined with the reason. A fix ships when the acceptance test passes on real material; no fix date is promised.

There is no bug bounty and no reward or recognition program; reporting never implies one. Responsible reporters are attributed in the release records when they want credit.

Release signing key

Every Isolith release artifact is signed with the release signing key before it is published. The fingerprint is published here so the key that signed your download is checkable: 

  Fingerprint: 9898A66D42D6FFD3EC5EA78278110F3ADAC1EE92
  Key id:      0x78110F3ADAC1EE92

The public key ships in the source repository at keys/oep-airgap-signing.pub.asc. Import it and retain only the fingerprint above; a signature by any other key means the artifact did not come from the Isolith release lane.

Where the private key lives, who may use it, and the rotation and compromise procedure are documented in docs/release-signing.md in the repository. The private key lives on the release lane build host, never in a repository, never in CI, and only the release lane may sign with it.

How to verify a download

gpg --import keys/oep-airgap-signing.pub.asc
# confirm the imported fingerprint is:
# 9898A66D42D6FFD3EC5EA78278110F3ADAC1EE92
gpg --verify-options show-fingerprint --verify <file>.sig <file>

For the air-gap bundle, the included airgap-verify.sh script imports the key and performs the detached verification for you. Every release also ships a SHA256SUMS file; the download page covers checksum verification as well.

Security posture, in plain words

Telemetry is off by default. No component phones home. Releases carry an SBOM derived from the committed dependency lock, a CVE scan, and an export-control classification file, checked in CI before anything ships. The attestations behind each claim, including what is not claimed, are the records cited in SECURITY.md. The self-conducted pentest day is a self-assessment of a specific build, not a third-party audit and not a standing certification.

The one-paragraph export-control statement is on the download page.
