Security

Security and release verification

This page tells you two things: how to report a security issue, and how to prove that a release you downloaded was really made by the Isolith release lane. The full policy lives in SECURITY.md in the repository.

Reporting a security issue

Do not open a public issue or pull request for an exploitable weakness. Report it privately to the maintainers at the address in SECURITY.md, and expect a reply within the response window the policy commits to. A report reaches the maintainer explicitly, so the safe harbor in the policy applies from the moment it is sent privately.

Release signing key

Every Isolith release artifact is signed with the release signing key before it is published. The fingerprint is published here so the key that signed your download is checkable: 

  Fingerprint: 9898A66D42D6FFD3EC5EA78278110F3ADAC1EE92
  Key id:      0x78110F3ADAC1EE92

The public key ships in the source repository at keys/oep-airgap-signing.pub.asc. Import it and retain only the fingerprint above; a signature by any other key means the artifact did not come from the Isolith release lane.

Where the private key lives, who may use it, and the rotation and compromise procedure are documented in docs/release-signing.md in the repository. In short: the private key lives on the release lane build host, never in a repository, never in CI, and only the release lane may sign with it.

How to verify a download

gpg --import keys/oep-airgap-signing.pub.asc
# confirm the imported fingerprint is:
# 9898A66D42D6FFD3EC5EA78278110F3ADAC1EE92
gpg --verify-options show-fingerprint --verify <file>.sig <file>

For the air-gap bundle, the included airgap-verify.sh script imports the key and performs the detached verification for you. The measured capability matrix and the install paths are on the other pages; verification is the step that makes a download trustworthy before any of them run.

Security posture, in plain words

Telemetry is off by default. No component phones home. Releases carry an SBOM derived from the committed dependency lock, a CVE scan, and an export-control classification file, checked in CI before anything ships. The attestations behind each claim, including what is not claimed, are the records cited in SECURITY.md.
