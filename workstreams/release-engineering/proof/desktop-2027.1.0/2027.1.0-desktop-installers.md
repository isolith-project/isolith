## 5. Update channel — round trip proven

GITHUB-PRIMARY-MIGRATION is blocked (no GitHub repo yet), so the signed
manifest is exercised against the canary release store end-to-end; switching
the source to GitHub Releases is a one-line config change once the migration
lands. Proven paths (oep-update-check + signed bundle + committed pubkey
`e84406ed...`):
- installed 2027.1.0 -> bundle offers 2027.1.0.1 -> `UpdateAvailable`
- installed 2027.1.0.1 -> same bundle -> `UpToDate`
- tampered bundle (payload byte flipped) -> `Untrusted` (hash mismatch)
- tampered bundle (signature invalidated) -> `Untrusted`
The signed bundle was attached to the canary release and fetched over HTTP
(RemoteUrl). Bundle: `dist/2027.1.0-desktop/signed/update-2027.1.0.1.bundle.json`.

## 7. Reproducibility (re-run, installers included)

Controlled comparison: two fresh CARGO_TARGET_DIR builds from `git archive
HEAD` (identical source + lock + toolchain).
- Raw Linux binaries: BYTE-IDENTICAL (oep-cgr2gltf, oep-shell workbench
  verified).
- Raw Windows x86_64 exe: NOT byte-identical — PE header timestamp, CodeView
  RSDS record and version-resource timestamps embedded at link time by mingw
  (verified by diffing byte offsets); code content deterministic.
- AppImage: NOT byte-identical across two builds (embedded timestamps).
- .deb: NOT byte-identical (member timestamps).
- MSI: NOT byte-identical (timestamps/GUIDs).

So: source binaries are reproducible; installers are not byte-identical, as
expected, and this record says so rather than claiming otherwise.
