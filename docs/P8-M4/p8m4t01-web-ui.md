# P8-M4-T01: PDM Web UI (item explorer, BOM tree, viewer embed, compare view)

Status: implemented (GREEN, verified on the reference vertical fixture).
Owner: P8 PDM lane. Version: 2 (2026-10-18).

## 1. What this card delivers

The browser face of the self-hosted PDM (ENOVIA-lite): a web UI served by the
same axum service that serves the P8 REST API v1 contract, plus the P6 viewer
embed for real oep-geo models. New crate `crates/oep-web` (binary `oep-web`):

    GET /                                 item explorer (vault catalogue)
    GET /ui/items/{item_id}               item detail (metadata, revisions,
                                          BOM tree, embedded viewer, compare links)
    GET /ui/items/{item_id}/bom[?rev=]    BOM tree, walked from the PDM
                                          relationship graph (oep-pdm::graph)
    GET /ui/items/{item_id}/preview/{rev}  viewer embed: renders the stored
                                          oep-geo model at that revision through
                                          oep_viewer (reference CPU rasterizer)
                                          to a PNG (X-Oep-Drawn-Pixels header)
    GET /ui/compare?item={id}&a={revA}&b={revB}   compare view for two revisions

The REST API v1 (`/api/v1/*`) is merged in unchanged, so the P7/P8 contract
clients keep working against the same server and port.

## 2. How the four acceptance points are met

- Item explorer: `GET /` lists the vault catalogue from the same `VaultStore`
  the REST API uses, newest first, with links into each item page.
- BOM tree: `GET /ui/items/{id}/bom` builds an `oep-pdm::graph::RelationshipGraph`
  from the item's real oep-geo document (`from_oepgeo_document`), then walks it
  top-down with the `children()` accessor this card adds to the graph (parent to
  composed children, with per-edge quantity), rendering a nested tree. An
  optional `?rev=` lets the user walk a specific revision's BOM.
- Viewer embed: `GET /ui/items/{id}/preview/{rev}` loads the revision's file,
  parses it as an oep-geo `Document`, and renders it through the P6 viewer
  embed (`oep_viewer::scene::build_scene` + `render` + `encode_png`). The
  response is a real PNG with an `X-Oep-Drawn-Pixels` header proving the model
  actually drew pixels. Different revisions render different images.
- Compare view: `GET /ui/compare` shows two revisions of an item side by side
  (metadata table + embedded preview of each) and reports whether the file
  content matches or differs.

The `oep-web` binary is the single entry point (`oep-web [--addr ...]
[--persist-dir ...]`).

## 2.5 Security posture (SEC-AUTHZ-RESIDUAL, v2)

SECURE BY DEFAULT: the shipped `oep-web` binary serves its merged REST API v1
router behind the same P11-T03 RBAC boundary as the `oep-pdm` binary
(`oep_web::web::build_authorized_router` wires `oep_pdm::service::
build_authorized_router` plus the UI routes). Every request to `/api/v1/*` is
decided against the strict boundary authorizer before a contract handler runs
(403 cross-role / unauthenticated, 404 cross-tenant masked). The open contract
is reachable only via the explicit `--no-auth` opt-out, which prints a loud
startup warning (controlled test / air-gap use only).

The browser UI routes (`/`, `/ui/*`) remain reachable on the authorized boot:
they are a read-only HTML/PNG workbench surface whose gate awaits the P8-M3-T01
identity layer (which will carry a verified principal the gate can trust). Until
then the UI surface is served open but LAN-off by the loopback-bind default
(decision #10); publishing it is the operator's accepted-risk call. The default
boot's enforcement is proven by `crates/oep-web/tests/web_auth_boundary.rs`,
which re-runs the P11-T03 attack matrix against the shipped binary (all probes
denied 403/404, the UI root stays browsable, and `--no-auth` warns and opens).

## 3. Reference vertical fixture

The end-to-end acceptance (crates/oep-web/tests/web_ui_acceptance.rs) drives
the real server over ephemeral-port HTTP, seeded with the committed reference
vertical fixture: the golden bracket assembly
(`crates/oep-geo/tests/golden/example-bracket.oepgeo.json`) as an assembly with
two revisions (golden as rev 1, a geometry-mutated variant with one fewer
fastener as rev 2). It asserts:

1. explorer lists the item;
2. the BOM tree walks the relationship graph (top assembly -> bracket part +
   fastener-set -> x4 fasteners);
3. the viewer embed returns a valid PNG with drawn pixels, and rev 2's render
   differs from rev 1's;
4. compare view shows both revisions and reports the difference;
5. the REST API health still answers next to the UI.

Proof artifacts (committed, generated by `workstreams/P8-M4/proof/gen_proof.py`):
`explorer.html`, `bom.html`, `compare.html`, `preview-1.png`, `preview-2.png`.
