# P7-M5-T01: Power-user velocity budget

Card: P7-M5-T01 keyboard/command line UX pass (power-user velocity test:
30 common operations under N seconds, measured).

Status: DELIVERED (v1.0.0). Supersedes: none. Cross-references: the adopted
shell decision (P7-M1-T01 open-modeler-shell-eval-memo), the interchange
workbench command surface (P7-M2-T01), the PDM API contract stub (P7-M2-T02),
the wgpu headless renderer decision (P6-M5-T01), and the accessibility pass
card that follows this one (P7-M5-T02).

## What a "power user" does, measurably

A power user does not click: the power user drives the OEP interchange
workbench through its machine-callable command surface (the oep-shell
`workbench` example binary, P7-M2-T01), one typed command per action, and
feels every operation as wall-clock latency. This card converts that into a
measured bargain:

- The 30 common operations a power user performs every session, documented in
  P7-M5/velocity/ops.json, one op per row with its `cli`, its honest expected
  outcome (success / typed-pending / typed-failure), and its budget in
  seconds.
- A harness (P7-M5/velocity/run_velocity.py) that builds the real CLI binary,
  runs each of the 30 ops on this host, and records min / mean / p95 / max
  wall-clock seconds per op into P7-M5/velocity/report-velocity.json.
- A regression gate (P7-M5/velocity/compare_velocity.py) that re-runs the
  harness on demand and fails when any op misses its budget or slows down
  beyond tolerance versus the committed baseline
  (P7-M5/velocity/baseline-velocity.json).

The ops span the full power-user surface, not just the happy path: discovery
(help, journal), STEP load, 3DXML load (including a 72-part satellite
assembly), modern-era CGR latch (NIST STC-06 / STC-08, V5-6R2023), classic
CGR, the PDM save/open lifecycle against the local stub, the honest
"save pending" interchange lanes, and the error paths a power user hits daily
(missing file, unknown command, junk bytes to each lane). Slow failure would
be a bug; the catalog measures it.

## Budget: N seconds

Every op must hum below its budget in mean wall-clock seconds. Budgets by
class, with generous headroom so CI noise never trips them while an
order-of-magnitude regression still fails:

| class                                   | budget_s |
| ---                                     | ---      |
| discovery / pdm / save / error          | 1.0      |
| STEP / 3DXML / CGR real loads           | 5.0      |
| large assembly load (FM1, 72 parts)     | 10.0     |

Headline: 30 common operations, all under a 1.0 to 10.0 second budget
depending on class; the full catalog in one host in well under a second each
in practice.

## Regression policy

The velocity test doubles as a regression gate. Run on demand (compare
scripts are documented above and in the script docstrings) or in developer
pre-commit runs:

1. Hard budget: any op whose fresh mean exceeds its class budget fails.
2. Tolerance: any op whose fresh mean exceeds its baseline mean by more than
   1.5x AND by more than the 0.05 s absolute floor fails. The absolute floor
   stops 1 ms of noise on a 4 ms op from tripping the gate; a real many-x
   slowdown on any op still crosses it.
3. Skipped ops (corpus absent on the current host) are reported but never fail
   the gate: an op that cannot run is honest, a slow op is a regression.

Exit 0 = pass, 1 = regression(s). The gate was verified in both directions:
a same-host re-run passes, and a deliberately 20x-faster fake baseline fails
(3 real regressions surfaced, all on the genuinely slow loads).
